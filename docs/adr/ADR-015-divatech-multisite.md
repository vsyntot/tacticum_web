# ADR-015: Divatech как второй сайт общей установки Битрикс

Дата: 14.10.2026. Статус: accepted; contact-only production launch verified 14.10.2026 после STATEFUL release, принятой Nginx correction, полного 15-minute monitoring и dual BASE.
Основание: владелец запросил многосайтовость для divatech.space и принял реализацию плана от 13.10.2026.

## Решение

У `s1/tacticum.ru` и `s2/divatech.space` разные document roots, шаблоны, домены и публичные страницы. Ядро, административная система, модули и БД общие. Во втором корне ссылки на `bitrix`, `local`, `upload` первого. Это разделение сайтов, а не независимая граница доверия администраторов.

Исходник Divatech — экспорт Tilda. Публичный лендинг реализуется собственными PHP/CSS/JS с медиа и содержанием предоставленного архива. Язык English. Tilda scripts/forms, Google Fonts и внешние счётчики не переносятся. Контент редактируется в отдельном локальном компоненте; структурированный редактор инфоблоков для контента не входит в первый запуск.

Публичные файлы второго корня хранятся в `sites/divatech/`, общий код — в `local/templates/divatech`, `local/components/tacticum/divatech.page`, `local/lib/Tacticum/Divatech`. Привязка `s1/tacticum` сохраняется.

## Формы и границы

- Две формы используют один endpoint `divatech_lead.php` с различимым `kind=contact|callback`. Он принимает только `s2` и канонический HTTPS Origin Divatech. Явно недопустимый Origin нельзя обойти корректным Referer. Общий allowlist Tacticum не расширяется.
- Проверки: origin → существующий PUBLIC_LEAD_POST limiter → метод → JSON с лимитом 16 KiB → обязательный CSRF → типы/длины/consent → запись. JSON-ответ не содержит исходные персональные данные.
- Хранение — отдельный инфоблок `divatech_leads`, только s2, без публичных прав и индексации. ID через `tacticum_rest_get_iblock_id`. Новые элементы неактивны. UUID запроса и MySQL advisory lock обеспечивают идемпотентность повторов.
- Уведомления через отдельные `DIVATECH_LEAD` event/template, только s2. Письмо содержит ID заявки, без её PII. Статус `queued` означает постановку в очередь, **не доставку**. `NOTIFICATION=failed` требует операционной обработки. Результат API подтверждает сохранение заявки.
- Формы выключены по умолчанию. Включение требует server-owned настроек recipient/sender, policy/consent и решения о хранении данных. До этого работает контактная версия с email и телефоном из исходника.
- Запросы к Tacticum REST с контекстом s2 отклоняются. Nginx Divatech использует terminal named denial handler: установленный BitrixEnv перенаправляет голый 404 обратно в PHP через @fallback. Этот механизм включён в regression fixture. Nginx разрешает только свои публичные assets и свой endpoint под `/local/`; остальные общие API, upload и второй admin URL закрыты. Администрирование остаётся на Tacticum.
- Страница содержит сессионные токены: composite выключен для ответа, Cache-Control private/no-store; корень Divatech в Nginx проксируется напрямую, без чтения общего composite cache.

Существующий limiter имеет общую для проекта модель IP+session; отдельный WAF/CAPTCHA или распределённый антиспам не добавляется. Хранение закрытого инфоблока не даёт самостоятельной изоляции от общих администраторов Битрикс.

## Доставка и откат

Релиз STATEFUL. Текущий FILE_ONLY controller не получает разрешения менять БД/vhosts/симлинки. Отдельный builder создаёт пакет с двумя явными корнями и SHA-256 каждого файла. Он не выполняет apply и выдаёт `production_apply_ready=false`, пока нет точного инфраструктурного плана, backup/restore и approval.

Структура конфигураций соответствует BitrixEnv link-site: HTTP/HTTPS vhosts и Apache backend на 8887; default Tacticum остаётся на 8888. После изучения установленных задач для review выбрана адресная доставка готовых конфигов из `tools/divatech/infrastructure/`, а не запуск общего мастера: последний затрагивает shared TLS options, ACME checkout/hook и cron. Новые конфиги производны от установленных шаблонов; это осознанное отступление от общей рекомендации Битрикс пользоваться мастером, требующее принятия в exact plan и сохранения этих конфигов при последующих действиях BitrixEnv. Общий `local` link добавляется отдельно. Параметры CMS создаёт CLI API-миграция; системные ядро/настройки подключения БД не заменяются.

API-миграция имеет dry-run/apply/activate/verify/rollback, expected state hash и приватный журнал. Создаёт s2 неактивным. Legacy Bitrix API может иметь собственные транзакции: журнал и контроль до/после обязательны; ошибка не означает автоматическую атомарную отмену всего сценария. Запрещён слепой повтор после partial failure.

Откат удаляет только созданные сущности при доказанном отсутствии заявок и совпадении состояния; восстанавливает DOC_ROOT s1, включая NULL через D7. Если заявки уже есть, удаляющий rollback отказывается работать: закрыть s2 и сохранить данные для адресного восстановления. Полный дамп общей БД после поступления новых заявок Tacticum автоматически не восстанавливается.

После первого запуска общий код Divatech должен войти в reviewed Git/main и обе verified BASE copies **до** следующего FILE_ONLY deploy Tacticum. Иначе authoritative `local/` может удалить новый код. Второй корень пока обслуживается отдельным STATEFUL runbook; неизвестные `sites/` paths текущий controller отклоняет.

## Проверка

Локальная репетиция использует чистые main/iblock с production, синтетическую MySQL 8.4 БД, PHP 8.5 и отключённые агенты/почту. Проверены выбор сайта по Host, формы, повтор отправки, отказ удалять заявки, точное восстановление metadata и dump/restore синтетической БД. Проверки Nginx location precedence выполнены отдельно в контейнере; это не заменяет production `nginx -t`, `httpd -t`, TLS и post-deploy smoke.

# Chat API Contract

Дата фиксации: 21.05.2026

## Endpoint

`POST /local/rest/tacticum_chat.php`

Назначение: backend adapter между публичными chat surfaces и upstream AI endpoint `/tacticum/v1/chat_agent`.

## Security Flow

Runtime order:

1. `tacticum_rest_validate_origin()`;
2. `tacticum_rest_rate_limit_by_class('PUBLIC_CHAT_POST', 'tacticum_chat')`;
3. method check: only `POST`;
4. JSON parse;
5. `tacticum_rest_check_csrf($data, true)`;
6. payload validation;
7. outbound request through `tacticum_rest_post_json(...)`.

## Request

Required JSON:

```json
{
  "user_message": "Описание задачи",
  "sessid": "bitrix_sessid"
}
```

Optional fields:

```json
{
  "group_id": "uuid-or-upstream-id",
  "startAgent": "ITExpertAgent"
}
```

Validation:

- `user_message`: required, string after trim, max 2000 chars;
- `group_id`: optional, string after trim, max 64 chars;
- `startAgent`: optional, allowlist only: `ITExpertAgent`, `SalesConsultantAgent`, `TriageAgent`;
- non-POST requests return `405 method_not_allowed`;
- invalid JSON returns `400 invalid_json`;
- invalid fields return `400 validation_error`.

## Upstream Request

Base URL comes from `tacticum_rest_get_required_https_ai_url('AI_SERVICE_BASE_URL')`.

Target URL:

```text
{AI_SERVICE_BASE_URL}/tacticum/v1/chat_agent
```

If `startAgent` is provided, backend sends it as query param:

```text
?startAgent=ITExpertAgent
```

JSON body sent upstream:

```json
{
  "user_message": "Описание задачи",
  "group_id": "uuid-or-upstream-id"
}
```

`startAgent` is intentionally not duplicated in the upstream JSON body.

## Success Response

Backend passes through successful upstream JSON.

Expected successful shape:

```json
{
  "response": "AI answer",
  "group_id": "uuid-or-upstream-id",
  "bitrix_url": "https://tacticum.ru/offer/<element-code>/"
}
```

Frontend renders `response` as text, not HTML. Links for "Оформить заявку" and "Полный расчет" are generated by the chat runtime/surface modules.

## Controlled Errors

| Status | Code | Reason |
|---:|---|---|
| 400 | `invalid_json` | Request body is not valid JSON object |
| 400 | `validation_error` | Required/allowed field failed validation |
| 403 | `invalid_origin` | Origin/referer/host guard failed |
| 403 | `invalid_csrf` | Bitrix sessid check failed |
| 405 | `method_not_allowed` | Request method is not POST |
| 429 | `rate_limited` | Shared rate limit exceeded |
| 500 | `config_error` | HTTPS AI base URL is missing/invalid |
| 502 | `curl_error` | cURL transport failure |
| 502 | `upstream_timeout` | cURL timeout |
| 502 | `upstream_http_error` | Upstream returned non-200/empty response |
| 502 | `upstream_error` | Upstream returned invalid JSON |
| 502 | `upstream_contract_error` | Upstream JSON lacks `response`, `error` and `message` |

Frontend maps technical upstream failures to safe user copy and must not expose raw payload, stack trace, config or PII.

## Logging

- Custom runtime code in `/local` and public scripts must not write chat request/response payloads to file logs.
- Do not add `AddMessage2Log`, `error_log`, `file_put_contents`, `Debug::writeToFile`, `console.log/error/warn` for chat payload debugging.
- If temporary incident diagnostics are required, use a separate time-boxed task with explicit PII policy and remove diagnostics before closing the incident.

## Smoke Cases

- POST first message with `startAgent=ITExpertAgent` returns controlled success or upstream error.
- POST follow-up with `group_id` does not resend `startAgent`.
- GET returns `405 method_not_allowed`.
- Invalid `startAgent` returns `400 validation_error`.
- Overlong `group_id` returns `400 validation_error`.
- Missing/invalid `sessid` returns `403 invalid_csrf`.
- Simulated upstream timeout returns `502 upstream_timeout`.

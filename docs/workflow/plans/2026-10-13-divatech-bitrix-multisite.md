Дата обследования: 13.10.2026. Автор: project-manager. Адресат: владелец проекта и исполнитель внедрения.
Статус: verified — согласованный contact-only запуск выполнен в production; correction `DIVA-FIX-3c159bad6601`, smoke/monitoring/dual BASE/cleanup завершены. Формы выключены по принятому решению. Git review/merge, общий FILE_ONLY BASE и контроль через 24 часа — отдельные последующие действия.

QA early gate: обязателен для форм, разделения сайтов и общей БД.

## 1. Цель и рекомендуемое решение

Запустить `https://divatech.space/` на IP `31.128.42.179` как второй сайт существующей установки Битрикс, сохранив работу `tacticum.ru`. У сайтов будут разные публичные корни, шаблоны, домены, формы и SEO, но общие ядро, БД и административная система.

Архив — экспорт Tilda, а не резервная копия Битрикс. Восстанавливать его через Bitrix restore.php или импортировать поверх действующего сайта не нужно. Предлагается перенести страницу в самостоятельный шаблон/компонент Divatech и зарегистрировать сайт `s2`. Публикация только HTML-файла отдельным виртуальным хостом не закрывает требование многосайтовости Битрикс.

Схема соответствует режиму разных доменов с общим ядром, описанному в [документации Битрикс](https://docs.1c-bitrix.ru/pages/advanced/multisite.html). Общая БД и общие модули означают общую административную и эксплуатационную границу: это не изоляция двух независимых установок.

## 3. Целевая структура

Предлагаемые пути, которые окончательно фиксируются в dry-run после проверки установленного BitrixEnv:

```text
/home/bitrix/www/                         действующий Tacticum, s1
  bitrix/                                общее ядро, без правок
  upload/                                общее файловое хранилище Битрикс
  local/
    templates/tacticum/                  существующий шаблон
    templates/divatech/                  новый шаблон
    components/tacticum/divatech.page/   новый компонент лендинга
    lib/Tacticum/                        общие и отдельно ограниченные сервисы

/home/bitrix/ext_www/divatech.space/      отдельный публичный корень, s2
  index.php
  404.php
  .section.php
  .htaccess
  urlrewrite.php
  robots.txt
  sitemap.xml
  favicon.ico
  bitrix -> /home/bitrix/www/bitrix
  local  -> /home/bitrix/www/local
  upload -> /home/bitrix/www/upload
```

В Git публичные файлы второго корня предлагается хранить в `sites/divatech/`, общие template/component/service файлы — в существующем `local/`. Симлинки создаёт инфраструктурная миграция из точного allowlist, а не архив приложения. Существующий FILE_ONLY builder принимает только обычные файлы и не должен обходиться ради симлинков.

Картинки дизайна — внутри assets шаблона, чтобы не создавать лишних `b_file` записей. Файлы будущего редактируемого контента — через API Битрикс с учётом общей `upload/`. Произвольный копирующий или удаляющий rsync по `bitrix/local/upload` симлинкам запрещён.

Предлагаемые параметры s2:

| Поле | Значение |
|---|---|
| ID | `s2`, если повторная проверка подтверждает, что он свободен |
| Название | DIVA Technologies |
| Домены | `divatech.space`; www обслуживается отдельным редиректом |
| SERVER_NAME | `divatech.space` |
| DIR | `/` |
| DOC_ROOT | `/home/bitrix/ext_www/divatech.space` |
| Язык | `en`, как в исходном лендинге; совместимая UTF-8 культура |
| По умолчанию | `N`; s1 остаётся default |
| SORT | Предлагается 20 при текущем s1=1; выбор сайта доказывается Host-тестом, не только сортировкой |
| Шаблон | `divatech`, без глобального условия для s1 |
| ACTIVE | Сначала `N`, включение внутри закрытого проверочного окна |

`DIR` — URL-путь, `DOC_ROOT` — физический путь; смешивать их нельзя. Назначение параметров описано в [форме настройки сайта](https://dev.1c-bitrix.ru/user_help/settings/settings/sites/site_edit.php). Для s1 предлагается установить `DOC_ROOT=/home/bitrix/www` после снимка текущих значений и проверки на копии; это отдельное изменение БД в плане.

## 4. Пошаговый порядок работ

### Шаг 1. Зафиксировать исходники и границы поставки

Исполнитель: PM/DevOps; результат — воспроизводимый исходный пакет.

1. Повторить проверку SHA-256 ZIP и сохранить оригинал вне Git и webroot. Текущий staged-файл не включать в коммит плана или приложения.
2. При реализации адресно исключить ZIP из index/deploy, сохранив локальный исходник. Добавить проверку на попадание архивов-источников в артефакт; сверить actual remote drift, поскольку ZIP уже есть на production.
3. Включить удаление только этого production ZIP в exact plan с backup; не удалять все ZIP по маске. После применения URL должен отвечать 403/404.
4. Зафиксировать состав релиза, существующие версии, параметры сайтов, hash конфигураций Nginx/Apache, общее состояние health и критические URL Tacticum.
5. Завести отдельный ADR: shared core/DB/local/upload, доменная маршрутизация, ограничения endpoints, владельцы контента и двух целевых корней деплоя. Статус ADR до согласования — proposed.

### Шаг 2. Подтвердить условия переноса и приём заявок

Исполнитель: PM/Backend; результат — согласованный контракт работы сайта.

1. Проверить доступную редакцию и лимит сайтов в установленной лицензии Битрикс; ключ лицензии не копировать в отчёты. По количеству модулей нельзя надёжно определить лицензию.
2. Подтвердить, что ZIP используется как утверждённый источник внешнего вида и контента. Не переносить автоматически недействующие контакты, предложения, счётчики или документы 2022 года.
3. Проверить способ использования экспортированного кода Tilda. Её [документация экспорта](https://help-ru.tilda.cc/export) отдельно ограничивает изменение экспортированного кода и ставит работу штатных форм в зависимость от подписки/домена. Если перенос предполагает изменение такого кода, уточнить допустимость; альтернативой является собственная реализация согласованного дизайна из разрешённых материалов. Не объявлять механическое разрезание HTML гарантированно допустимым способом.
4. Рекомендуемый вариант форм — собственный приём в Битрикс, с независимыми Divatech получателями и настройками. Вариант сохранения Tilda возможен только после проверки аккаунта, активного приёмщика и домена; из архива это неизвестно.
5. До запуска определить получателя заявок, отправителя, текст согласия/политики и место хранения. Адреса/токены — в server-owned конфиге, не в репозитории.

### Шаг 3. Подготовить изолированную репетицию

Исполнитель: Backend/DevOps/QA; результат — рабочий второй сайт на проверочной копии.

1. Stage-хоста в проекте нет. Поднять локальную или временную изолированную копию вне публичного webroot с совместимыми PHP/MySQL, ядром и обезличенной БД. Это среда репетиции, а не новый обязательный публичный stage-хост.
2. Не запускать почту, cron, агенты, вебхуки и внешние интеграции production из копии. Секреты и backup не публиковать; дамп хранить с ограниченным доступом.
3. Воспроизвести два hostname и разные document roots. Проверить shared links, загрузку шаблонов, корректный SITE_ID и определение корней из админки/CLI.
4. Репетиция восстановления проверяет и БД, и файлы/config; распаковка только HTML не доказывает возможность отката STATEFUL-изменений.
5. Если репетиция недоступна, вынести конкретный остаточный риск в bounded waiver текущего релиза. Предыдущее согласие на отсутствие stage не подменяет результаты этой проверки или exact approval.

### Шаг 4. Подготовить страницу Divatech для Битрикс

Исполнитель: Frontend/Backend; результат — версия лендинга с сохранённым дизайном.

1. Создать `local/templates/divatech` с header/footer и корректным Bitrix head/asset lifecycle. Не копировать шаблон Tacticum со счётчиками и глобальными формами.
2. Создать тонкий `sites/divatech/index.php` и `tacticum:divatech.page`; перенести блоки лендинга в читаемые части компонента. Выбранный на шаге 2 способ работы с Tilda-кодом задаёт границу переиспользования.
3. CSS/JS подключать через `Bitrix\Main\Page\Asset`, сохранить порядок зависимостей и инициализации. Выделить inline инициализацию и стили в собственные assets там, где разрешено выбранным способом переноса.
4. Сохранить якоря, мобильное меню, слайдеры и анимацию; исправить пути картинок/CSS. Body-фрагмент использовать только по назначению; не публиковать дубликаты.
5. Для первого запуска контент может быть в отдельных include/частях шаблона, редактируемых с нужными правами. Если нужна структурированная редактура карточек из админки — согласовать модель отдельных инфоблоков Divatech, без присвоения сайта s2 всем инфоблокам Tacticum.
6. Настроить title, description, один H1, canonical, OG, favicon, 404. Старый `page28604425.html` перенаправлять 301 на `/` с сохранением query; `/files/page28604425body.html` не индексировать и не раздавать как самостоятельную страницу.
7. Составить список внешних ресурсов, проверить Dropbox-ссылку и загрузку шрифтов. Счётчик аналитики должен принадлежать Divatech; Tacticum-счётчик не наследовать автоматически.

### Шаг 5. Разделить настройки и поведение общего кода

Исполнитель: Backend/Architect; результат — отсутствие функционального смешения сайтов.

1. Общий `local/php_interface/init.php` сейчас подключает Tacticum helpers через `DOCUMENT_ROOT`. С общей ссылкой `local` он загрузится и для s2. Разделить нейтральный bootstrap и обработчики конкретного сайта.
2. Проверить хелперы URL/SEO и конфиг: сейчас `site_helpers.php` имеет fallback на `https://tacticum.ru`, а `Security::isAllowedHost()` допускает Tacticum. Ввести явный доверенный site context/config для Divatech; не строить canonical по непроверенному Host.
3. Для событий инфоблоков и cache invalidation проверять назначение сущности сайту, а не только текущий SITE_ID: события также запускаются в админке и CLI. Сохранить действующие обработчики s1.
4. Ключи кеша компонентов и собственных хранилищ включают SITE_ID и релевантные параметры. Сначала проверить сайт без композита, затем при необходимости отдельно проверить композит и кеш по Host.
5. На vhost Divatech закрыть Tacticum API/REST пути, которые не нужны второму сайту. Отдельный endpoint Divatech разрешить адресно. Серверная проверка site/host/прав дополняет nginx-ограничения; CORS сам по себе не является изоляцией.
6. Не расширять глобальный список origins так, чтобы Divatech автоматически получил доступ ко всем Tacticum endpoints.
7. Учесть общие пользователи/группы Битрикс; редактору Divatech выдать адресные права на его папки/контент. Административный канонический домен оставить Tacticum; поведение `/bitrix/admin/` на Divatech задать явно, не редиректить весь `/bitrix/`.
8. Проверить cookie Domain/Secure/SameSite, отсутствие навязанного cookie-domain Tacticum и нежелательного автоматического обмена авторизацией. Новую SSO-схему для лендинга не вводить.

### Шаг 6. Реализовать и проверить две формы

Исполнитель: Backend/QA; результат — подтверждённый путь заявки.

Рекомендуемая ветка, пока владелец не выбрал другой вариант:

1. Два отдельных `form_id` Divatech для обратного звонка и контактной заявки. Не использовать `adp-cta` и не направлять заявки в AI-продажу Tacticum по умолчанию.
2. Endpoint и сервис имеют явный Divatech site context. Последовательность: origin validation → rate limit → проверка метода/JSON → CSRF → проверка полей/согласия → сохранение → доставка.
3. Для сохранения использовать поддерживаемую сущность с закрытыми правами, например отдельный инфоблок заявок, созданный идемпотентной миграцией и связанный только с s2. ID получать по символьному ключу через конфиг/helper. Не предполагать наличие модуля `form`.
4. Письмо/CRM-уведомление получает собственные шаблоны/привязку s2, sender и recipient. Запись заявки подтверждается независимо от успеха внешней доставки; повторная отправка не создаёт неконтролируемые дубликаты.
5. Уведомления тестировать только по явно согласованному получателю с синтетическими данными. До этого — транспорт-заглушка/тестовое хранилище. Проверить обязательные поля, некорректный email/телефон, CSRF, rate limit, ошибку доставки, двойной клик и восстановление UI после ошибки.
6. Не писать payload и персональные данные в технические логи или GitHub artifacts. Срок хранения и доступ к реальным заявкам определить перед открытием форм.

### Шаг 7. Подготовить отдельный STATEFUL-пакет

Исполнитель: DevOps/Backend/QA; результат — точный проверенный пакет для approval.

1. Подготовить `dry-run/apply/verify/rollback` миграции с журналом созданных объектов и до/после значениями. Записи сайтов/шаблонов/инфоблоков менять штатными API Битрикс; прямой SQL использовался только для read-only обследования.
2. Описать две файловые цели: shared additions в `/home/bitrix/www/local/` и публичные файлы `/home/bitrix/ext_www/divatech.space/`. Отдельно перечислить config, DB rows, symlinks и адресное удаление ZIP.
3. Разделить состав artifact, конфигурацию сервера и данные. Зафиксировать digest artifact, scope version, expected PROD state, plan_id, срок действия approval, все удаления и обратные действия.
4. Текущий GitHub controller поддерживает только FILE_ONLY. Не расширять его права молча и не пытаться выполнить DB/vhost/symlink миграцию через него. Первый запуск провести отдельной проверенной STATEFUL-процедурой.
5. До публикации общего `local/` обеспечить, чтобы последующий деплой Tacticum с authoritative `local` не удалил новый шаблон/компоненты Divatech. Все общие файлы должны быть отражены в согласованном Git baseline; для второго корня нужен отдельный управляемый manifest/delivery mapping.

## 5. Откат

Откат должен быть адресным: полное восстановление общей БД может уничтожить новые заявки и изменения Tacticum, сделанные после backup.

1. Закрыть Divatech для посетителей на уровне его vhost и отключить его формы; Tacticum продолжает работать.
2. Вернуть предыдущие vhost/settings только затронутого scope, проверить синтаксис и reload. Не откатывать сертификат Tacticum и не удалять общий ACME renewal state целиком.
3. Деактивировать s2 и отвязать созданный шаблон. При ошибке до приёма реальных данных — обратная миграция по журналу ID/значений; никогда не удалять «всё с похожим названием».
4. Если заявки уже поступили, сохранить их и приостановить удаление соответствующих сущностей. Решение о полном DB restore возможно только в отдельном аварийном окне с планом сохранения новых записей.
5. Вернуть изменённые shared файлы, параметры s1 и конфиг; удалить только добавленные файлы из утверждённого manifest. При удалении symlink удалять саму ссылку, не её target.
6. Если DNS не менялся, DNS rollback не нужен. Для Divatech оставить понятную закрытую страницу на его собственном vhost, чтобы он снова не показывал Tacticum.
7. Повторить Tacticum smoke, сохранить rollback evidence и снять lock после верификации.

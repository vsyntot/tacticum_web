# Tacticum Forum — диалоговая платформа для клиентских коммуникаций

> Импортонезависимая программная платформа автоматизации обработки входящих клиентских обращений. Сценарные диалоговые боты с обогащением большими языковыми моделями (LLM). Классы 04.13 «Системы управления процессами организации», 04.11, 02.09. Подаётся в Единый реестр российских программ для ЭВМ и БД.

## Slide 2 — Проблема: между сценарными ботами и «чистыми LLM»

**Сегодня в обслуживании клиентов через цифровые каналы — две крайности, и обе не работают:**

| Подход | Что обещает | Где ломается |
|---|---|---|
| **Классические сценарные боты** | Контролируемые ответы, predictable UX | Жёсткое дерево из 200+ узлов. Любое отклонение → «не понимаю вас». Стоимость поддержки растёт линейно |
| **Чистые LLM-боты на API** | Естественный диалог, «можно поговорить о чём угодно» | Галлюцинации в проде. Невозможно гарантировать корректный ответ на критичный вопрос. Аудиторий с регуляторикой — недоступно |
| **Live-чат с операторами** | Качество, но дорого | Операторы тонут в типовых обращениях. SLA рушится на пике |

**Контакт-центры и службы клиентской поддержки в 2026 году:**

- 60–80% обращений — типовые (статус заказа, политика возвратов, тарифы, FAQ).
- Стоимость минуты оператора растёт быстрее автоматизации.
- Регуляторы требуют traceability ответов в финансах, страховании, госуслугах.
- Импортные платформы (Twilio Flex, Genesys Cloud, Salesforce Service Cloud) больше нельзя использовать — нужны замены.

## Slide 3 — Решение: сценарии + LLM, без иллюзий

Tacticum Forum — гибридный подход: жёсткие сценарные графы для критичных путей + LLM-обогащение для распознавания намерения, обработки уточнений и автоматического выявления новых потребностей.

**Архитектурно** — это тонкое приложение поверх Tacticum Platform: сценарий описывается как декларативный манифест с расширенным DSL (узлы Start / Message / Input / Condition / Interrupt / Checkpoint / End), а исполняется тем же Agent Runtime, который Tacticum Agents использует для агентов. ## Slide 5 — Метрики, которые двигаем

Tacticum Forum проектировался под измеримые показатели, а не «общую удовлетворённость».

| Метрика | Что измеряет | Куда движется при правильной настройке |
|---|---|---|
| **Automation rate** | Доля обращений, закрытых без оператора | 40–70% по индустрии (зависит от продукта) |
| **Drop-off rate** | Доля диалогов, прерванных клиентом до решения | −20–40% после первой итерации сценариев |
| **Time to resolution** | Время от первого сообщения до закрытия диалога | −50–70% на автоматизируемых сценариях |
| **First contact resolution** | Доля обращений, решённых с первого касания | +15–25 п.п. на типовых обращениях |
| **Доля передач оператору** | Сколько диалогов эскалируется | −30–50% после настройки сценариев |
| **Cost per contact** | Себестоимость одного обращения | −30–60% на типовом потоке |

### Индустриальный benchmark

| Источник | Метрика |
|---|---|
| Gartner (CX Predicts 2025) | К 2026 году **30%** взаимодействий контакт-центров — полностью AI-разрешённые |
| McKinsey (State of AI in CX, 2024) | Снижение operating cost контакт-центра при гибридной AI-автоматизации — **20–40%** |
| Forrester (CX Conversational AI, 2024) | First contact resolution на гибридных ботах vs чистых сценарных — **+20 п.п.** |

## Slide 6 — A/B-тесты и аналитика

**Главная проблема contact-center automation:** «мы поменяли сценарий, и метрика поплыла. Почему?»

Tacticum Forum закрывает этот разрыв встроенными A/B-инструментами на уровне самой платформы.

### Что можно проверять

| Гипотеза | Как тестируем |
|---|---|
| Новый вариант формулировки повышает first-contact-resolution | Сплит 50/50, метрика FCR, статсиг |
| Изменение порядка чекпоинтов снижает drop-off | Сплит 30/70 (на текущий сценарий — больше), метрика drop-off в каждом чекпоинте |
| Новый chekpoint перед эскалацией снижает передачи оператору | Сплит, метрика escalation rate, контроль time-to-resolution |
| Обогащение LLM на узле X повышает понимание | Сплит «классический сценарий» vs «LLM-обогащённый», метрика рaspознавания намерения |

### Что внутри подсистемы

- Доменная модель «эксперимент / вариант / правило сплита / метрика / период наблюдения».
- Детерминированный сплит (по идентификатору диалога) и рандомизированный (с контролем доли).
- Сбор событий в разрезе варианта: доходимость до чекпоинтов, drop-off, передачи оператору, удовлетворённость.
- Расчёт статсиг между вариантами с защитой от p-hacking.
- Контроль состояний эксперимента: создание → запуск → остановка → завершение.
- Защита от одновременного запуска конфликтующих экспериментов на одном сценарии.

### Воронка по чекпоинтам

Аналитика разбивает диалог на ключевые этапы (чекпоинты) и показывает, на каком шаге теряется аудитория. Из любой агрегированной метрики — переход в конкретный диалог в журнале для drill-down.

## Slide 7 — Отрасли и кейсы (benchmark-уровень)

> Конкретные кейсы заказчиков фиксируются по мере подписания соглашений о публичности. Ниже — индустриальный benchmark по типовым внедрениям.

### Контакт-центры e-commerce

- **Типовой поток:** статус заказа, политика возвратов, информация о продукте, изменение доставки.
- **Эффект по benchmark:** automation rate 50–70%, снижение нагрузки операторов на 40%, drop-off −25%.
- **Каналы:** Telegram, веб-чат, мобильное приложение.

### Финансовые организации (банки, страховые)

- **Типовой поток:** баланс/выписка, статус заявки, FAQ по продуктам, навигация по тарифам.
- **Эффект по benchmark:** automation rate 35–50%, FCR +20 п.п., регуляторный аудит ответов через журнал.
- **Каналы:** мобильное приложение, веб-чат, SIP-телефония.

### Телеком

- **Типовой поток:** баланс, тарифы, активация услуг, обращения по качеству связи.
- **Эффект по benchmark:** automation rate 45–60%, снижение AHT (average handle time) операторов на 20–30% на эскалациях.
- **Каналы:** мобильное приложение, веб-чат, IVR, SMS.

### Государственные и муниципальные сервисы

- **Типовой поток:** статус заявления, навигация по услугам, FAQ по документам.
- **Эффект по benchmark:** automation rate 40–55% при правильно описанной карте потребностей.
- **Каналы:** портал, мобильное приложение, чат-боты в мессенджерах.

### Внутренний саппорт (HR, IT helpdesk)

- **Типовой поток:** статус заявки, FAQ по политикам, навигация по корп-документам.
- **Эффект по benchmark:** automation rate 50–70% за счёт ограниченного словаря и качественной FAQ-базы.
- **Каналы:** Telegram, корп-портал, MAX, VK Teams.

- On-prem-поставка — полная изоляция от зарубежной инфраструктуры, включая sovereign LLM.

> **ClickHouse для аналитики.** На текущем этапе ClickHouse-агрегаты — внутри Forum. Архитектурно это кандидат на платформенный модуль `analytics_warehouse`, если в линейке Tacticum появится второе приложение, требующее CH-аналитики. Для заказчика это прозрачно: один дистрибутив, один контур.

## Slide 10 — С чего начинаем

### Этапы внедрения

| Этап | Срок | Что внутри |
|---|---|---|
| **Discovery + dataset assessment** | 1–2 недели | Аудит текущего потока обращений, карта потребностей, выбор 1–2 пилотных сценариев |
| **Pilot** | 4–6 недель | Один сценарий в production на ограниченной аудитории, A/B-тесты, итерации |
| **Integration** | 1–2 месяца | Подключение к CRM/ERP/каналам, развёртывание в контуре заказчика |
| **Production rollout** | 2–4 месяца | Раскатка на полный поток, обучение операторов, передача наблюдаемости |

### Кого со стороны заказчика нужно подключить

| Роль | Зачем |
|---|---|
| Руководитель контакт-центра / CX-директор | Спонсор, постановка задач, приёмка |
| Аналитик процессов | Карта потребностей, чек-листы сценариев |
| IT-архитектор | Интеграции с корп-системами и каналами |
| Безопасность | Согласование контура и аудит-политик |

### Cascade-ask

```
1️⃣  DISCOVERY (60-90 минут)
    └─ Card-board вашей текущей карты обращений
       Выбор 1-2 топ-сценариев по объёму потока
       
2️⃣  PILOT (4-6 недель)
    └─ Один сценарий в продакшене
       Реальные метрики, реальная итерация на сценарии
       
3️⃣  INTEGRATION + ROLL-OUT
    └─ Подключение к CRM/каналам
       Раскатка на полный поток
       
4️⃣  CONTINUOUS OPTIMIZATION
    └─ A/B-тесты как часть операционного процесса
       Авто-выявление новых потребностей
       Регулярное обновление сценариев
```

**Что нужно от заказчика для старта:**

1. Описать текущий поток обращений (объём, каналы, типовые тематики).
2. Назначить владельца со стороны контакт-центра / CX-направления.
3. Подготовить корп-документы / FAQ / шаблоны ответов для RAG.
4. Согласовать контур развёртывания (SaaS / on-prem / гибрид).

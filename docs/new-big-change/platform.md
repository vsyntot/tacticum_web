## Slide 2 — Контекст: «свой собственный AI-стек» сегодня

В каждой крупной организации, строящей продукты с применением LLM, повторяется один и тот же сценарий:

- разные команды используют разные LLM-провайдеры — нет единого учёта стоимости;
- каждая команда самостоятельно поднимает MCP-серверы, RAG, память;
- идентификация пользователей и арендаторов реализована отдельно в каждом продукте;
- нет единой наблюдаемости вызовов LLM и единого аудита;
- инфраструктура для on-prem-поставки одного продукта тащит в себе полную копию всей AI-инфраструктуры.

**Результат:** одни и те же баги фиксятся в трёх местах; пилотный проект на 8 недель превращается в 6 месяцев; экспертиза по безопасности проходится отдельно для каждого продукта.

## Slide 3 — Решение: единое инфраструктурное ядро

Tacticum Platform выносит в общее ядро всё, что повторяется в двух и более AI-приложениях, и предоставляет это как сервисы и SDK для прикладных команд. 17 модулей сгруппированы в 6 категорий по типу ответственности.

```
┌─────────────────────────────────────────────────────────────────────┐
│                      TACTICUM PLATFORM (ядро)                       │
│                                                                     │
│  RUNTIME   │ Agent Runtime · MCP Runtime · Workflow Spec Engine     │
│  ──────────┼──────────────────────────────────────────────────────  │
│  AI        │ LLM Gateway · Prompt Management · Guardrails           │
│  ──────────┼──────────────────────────────────────────────────────  │
│  DATA      │ Knowledge / RAG · Memory Service · Doc Processing      │
│  ──────────┼──────────────────────────────────────────────────────  │
│  ACCESS    │ Identity & RBAC · Tenancy & Quotas · Credential Pool   │
│  ──────────┼──────────────────────────────────────────────────────  │
│  IO        │ Connectors · Event Bus · Embedded MCP Servers          │
│  ──────────┼──────────────────────────────────────────────────────  │
│  OPS       │ Observability & Cost Tracking · Platform SDK           │
└─────────────────────────────────────────────────────────────────────┘
            ▲                       ▲                       ▲
       Agent Manifest         Profile +              Scenario Manifest
       (декларация)         Workflow Manifest        (декларация)
            │                       │                       │
       Tacticum                Tacticum                Tacticum
       Agents                    Dev                    Forum
```

**Принцип:** прикладные приложения **не реализуют движки** — они описывают свои графы, сценарии и workflow как декларативные манифесты. Платформа исполняет.

**Один Agent Runtime — три словаря.** Agents даёт манифест графа агента, Forum — манифест сценария (с узлами Message / Input / Condition / Checkpoint), Dev — манифест analysis-subagents. Исполняет один универсальный движок.

## Slide 4 — Архитектура: что внутри ядра

| Группа | Подсистема | Назначение |
|---|---|---|
| **RUNTIME** | **Agent Runtime** | Generic-движок исполнения декларативных графов с ConversationState, checkpointing, привязкой MCP-инструментов. Используется Agents, Forum, Dev — один движок, три DSL |
| | **MCP Runtime + Registry** | Среда исполнения MCP-серверов и каталог совместимости. Scope-aware вызовы инструментов, аудит |
| | **Workflow Spec Engine** | Durable-движок долгоживущих workflow с фазами утверждения. Поддерживает human-approval-этапы, может длиться дни/недели |
| **AI** | **LLM Gateway** | Единый OpenAI-/Anthropic-совместимый API. Маршрутизация на провайдеров, failover, квоты, контроль стоимости |
| | **Prompt Management** | Версионируемый реестр промптов с метками (production/staging/canary), кэш в Redis. Langfuse-совместимый |
| | **Guardrails** | Политики валидации входа и выхода LLM на уровне арендатора. Маскирование, блокировка, эскалация |
| **DATA** | **Knowledge / RAG** | Семантический + полнотекстовый поиск (Qdrant + Meilisearch + reranker). Ingestion-конвейер |
| | **Memory Service** | Типизированная корпоративная память, привязанная к scope `tenant/account/project/user`. Memory MCP |
| | **Document Processing** | Извлечение текста из PDF/DOCX/XLSX/PPTX. Единый сервис для RAG ingestion и прикладных приложений |
| **ACCESS** | **Identity & RBAC** | OIDC через Authentik, API-токены, AuthScope в каждом вызове. SSO на все продукты |
| | **Tenancy & Quotas** | Иерархия `Tenant → Account → Project → User`. Изоляция данных на query layer, квоты по LLM-токенам |
| | **Credential Pool** | Зашифрованное хранилище ключей LLM-провайдеров. Ротация без переналадки приложений |
| **IO** | **Connectors** | Telegram, веб-чат, SIP, MAX, VK Teams, webhook-роутер. Единая абстракция сообщения |
| | **Event Bus** | Доменные события между подсистемами и приложениями. Pub/sub, retention, replay для аудита |
| | **Embedded MCP Servers** | First-party MCP-сервера: Excel, Word, PowerPoint, Project, Wiki, Memory, Transcription, Filesystem |
| **OPS** | **Observability & Cost** | Span-based трассировка LLM-вызовов, биллинг по LLM-токенам, дашборды стоимости |
| | **Platform SDK** | Python + TypeScript библиотеки для прикладных приложений. Типизированные клиенты ко всем сервисам |

## Slide 5 — Что заказчик получает (бизнес-эффект)

| Подсистема | Что заменяет в текущем стеке | Эффект для бизнеса |
|---|---|---|
| LLM Gateway + Credential Pool | Прямые SDK провайдеров в каждом приложении | Один контракт, единый учёт стоимости, безопасная ротация ключей |
| MCP Runtime + Registry | Локальные `.mcp.json` в каждом проекте | Каталог MCP-серверов как сервис арендатора, audit-trail вызовов |
| Identity & RBAC | Отдельная аутентификация в каждом приложении | Один SSO; единый источник истины по пользователям |
| Tenancy & Quotas | Самописная мультитенантность в каждом приложении | Один контракт изоляции данных, обязательное условие SaaS-поставки |
| RAG / Knowledge | Точечные интеграции с Qdrant в каждом приложении | Единый индексатор корпоративного контента |
| Memory Service | Отсутствует / ad-hoc | Корпоративная память с правами по scope |
| **Agent Runtime + Workflow Spec Engine** | Локальные обвязки LangGraph в каждом приложении + ручные workflow | Один движок диалогов и один движок workflow на всех; приложение описывает граф/сценарий/workflow как **декларативный манифест** |
| Event Bus | Прямые вызовы между приложениями или их отсутствие | Cross-app коммуникация по доменным событиям; audit/replay; loose coupling |
| Embedded MCP Servers | Каждое приложение пишет свои парсеры Office/Wiki | Готовый набор tool-инструментов «из коробки» доступен всем приложениям |
| Observability & Cost | Логи в файлах, ручной подсчёт | Один источник правды по затратам на LLM и качеству генерации |

**Сводный эффект:** время вывода нового AI-приложения сокращается с 3–4 месяцев на инфраструктуру до 2–4 недель.

**Архитектурный принцип:** прикладные приложения **запрещают себе** прямые вызовы LLM-провайдеров, локальное хранение ключей, собственную мультитенантность, собственный OIDC, локальные MCP-сервера. Эти конструктивные ограничения и делают платформу платформой.

## Slide 7 — Sovereign LLM

Платформа работает с тремя категориями моделей через единый шлюз:

| Категория | Примеры | Где исполняется |
|---|---|---|
| **Российские облачные** | GigaChat (Сбер), YandexGPT, MTS AI, T-Bank LM | В контуре провайдера РФ |
| **Open-source в контуре заказчика** | Qwen, Kimi, DeepSeek, Llama, Mistral | На серверах заказчика (vLLM/SGLang) |
| **Зарубежные облачные (опционально)** | OpenAI, Anthropic, Google | Только если разрешено политикой арендатора |

Маршрутизация настраивается на уровне арендатора. Для контуров с ограничениями на трансграничный трафик зарубежные облачные модели запрещаются на уровне политики; шлюз отказывает в обращении до сетевого вызова.

## Slide 8 — On-prem-поставка

Дистрибутив поставляется в виде набора контейнерных образов и манифестов оркестрации.

| Параметр | Значение |
|---|---|
| Поддерживаемые серверные ОС | Astra Linux Special Edition / Common Edition, РЕД ОС, ОС «Альт» |
| Архитектура процессора | x86-64; ARM64 — по запросу |
| Минимальные требования пилотного контура | 16 ядер CPU, 64 ГБ RAM, 500 ГБ SSD, GPU опционально для inference open-source LLM |
| Среда оркестрации | Docker Compose (для пилотов), Kubernetes (для продакшен-нагрузок) |

Развёртывание в изолированном контуре заказчика без обращения к зарубежным сервисам поддерживается полностью.

## Slide 9 — Доказательство: на платформе уже работают прикладные продукты

Платформа не «строится в надежде на пользователей». Она — рабочая основа для трёх собственных прикладных продуктов правообладателя:

- **Tacticum Agents** — мультиагентные ассистенты для HR/юр/бух/саппорт. Описывает свои графы как Agent Manifest, исполняется на Platform Agent Runtime. Использует LLM Gateway, MCP Runtime, Memory, Connectors.
- **Tacticum Dev** — agentic development lifecycle. Использует Identity & RBAC, MCP Runtime (хостит свои Stack-Specific MCP Bundles и Design Token Layer), Knowledge как backbone для RE Knowledge DSL, Workflow Spec Engine для Feature Lifecycle.
- **Tacticum Forum** — диалоговые сценарные боты для контакт-центров. Описывает сценарии как Scenario Manifest (расширенный DSL поверх Agent Manifest), исполняется на том же Platform Agent Runtime. Использует LLM Gateway, RAG, Connectors.

**Архитектурное доказательство:** один Agent Runtime обслуживает Agents (мультиагентность), Forum (real-time клиентский диалог), Dev (analysis-subagents). Это и есть «платформенный эффект» — повторное использование, проверенное тремя разными нагрузками.

Каждый продукт — отдельная запись в Реестре отечественного ПО. Платформа — общая основа.

**Что это значит для заказчика:** инфраструктура валидирована на трёх production-нагрузках с разными профилями (фоновая мультиагентность, разработческий workflow, real-time диалоги). Нет «hello world» в качестве референса.

## Slide 10 — Модель поставки и старт

| Этап | Срок | Что внутри |
|---|---|---|
| **Discovery** | 1–2 недели | Аудит текущего AI-стека, оценка готовности к платформе, целевая архитектура |
| **PoC** | 4–6 недель | Развёртывание ядра в стенде заказчика; перенос 1 приложения на платформу как референс |
| **Pilot** | 2–3 месяца | Production-перевод 2–3 приложений, обучение команды, передача SDK |
| **Production rollout** | 4–6 месяцев | Перевод оставшегося AI-стека, выход на единые SSO/учёт стоимости/аудит |

**Модели коммерческой поставки:**

- **On-prem лицензия** — постоянное право использования + ежегодная поддержка.
- **SaaS подписка** — для пилотных контуров и небольших арендаторов.
- **ПАК** — дистрибутив с предустановленным окружением для субъектов КИИ.

**Что нужно от заказчика для старта:**

1. Уточнить целевой сценарий (новое AI-приложение / консолидация существующих).
2. Назначить владельца со стороны заказчика (CIO / руководитель AI-направления).
3. Подготовить пилотный стенд (виртуальная инфраструктура или dedicated hardware).
